Concept & Theory: File Upload

Overview

A file upload vulnerability exists when a website lets users upload files (images, documents, avatars, etc.) but fails to properly control what gets uploaded, where it's stored, or what happens when it's later accessed. Because the attacker fully controls the file's name, content, and metadata, any weakness in how the server checks these things can be abused — ranging from defacing a site to gaining full remote control of the server.

The danger level depends entirely on what the server does with the file afterward:

  • If it just stores/displays it → usually low risk
  • If it executes it as code, or lets it be used to read/write other files → high to critical risk
Core Variants

1. No Validation At All

What it is: The simplest and most dangerous case — the server accepts any file, with no check on extension, type, or content whatsoever.

How it works: An attacker uploads a working web shell (e.g. a PHP script) directly, with no disguise needed. If the server later executes files from that folder, visiting the file's URL runs the attacker's code immediately.

Why it happens: Developers sometimes build the upload feature quickly and assume "we'll add validation later" — and never do, or they only validate on the front-end (JavaScript), which is trivial to bypass since the attacker can send the raw request directly.

2. Flawed File-Type Validation (Extension-Based Bypass)

What it is: The server does check the file extension, but the check is incomplete — usually because it's a blacklist (a list of "bad" extensions to block) rather than a whitelist (a list of "good" ones to allow).

How it works: Attackers exploit gaps in the blacklist:

  • Case tricks: shell.PHP instead of shell.php
  • Alternate executable extensions: .phtml, .php5, .pht
  • Double extensions: shell.php.jpg
  • Encoding tricks: shell.php%00.jpg, trailing dots

Why it happens: Blacklists try to predict every dangerous possibility, but there are always extensions or quirks a developer didn't think to include — a fundamentally weaker approach than only allowing a small known-safe list.

3. Web Shell Upload via Content-Type Bypass

What it is: The server checks the Content-Type header sent with the file (e.g. expecting image/jpeg) instead of — or in addition to — the filename.

How it works: This header is just text the browser sends along with the file — completely controlled by the attacker. Using a proxy tool like Burp Suite, the attacker intercepts the upload request and simply changes:

Content-Type: application/octet-stream to Content-Type: image/jpeg

...while keeping the filename shell.php and the actual PHP code inside unchanged. The server sees a "trusted" label and lets it through.

Why it happens: The Content-Type header is a claim, not a fact. Trusting it without inspecting the real file content is the mistake.

4. Path Traversal via Filename

What it is: The server saves the uploaded file using the filename the attacker provided, without sanitizing it — allowing the attacker to control where on the server the file actually lands.

How it works: Instead of a normal filename, the attacker uploads a file named: ../../var/www/html/shell.php

The ../ sequences tell the filesystem to move up and out of the intended uploads/ folder. If unsanitized, the file can land in a directory where scripts are executed — even if the original uploads folder was properly locked down.

Example:
Normally: /var/www/html/uploads/images/photo.jpg
Attacker provides filename: ../../shell.php
Server constructs path: /var/www/html/uploads/images/../../shell.php
Filesystem resolves to: /var/www/html/shell.php (escaped the uploads directory!)

Why it happens: Developers often secure the upload folder itself (e.g. disabling script execution there) but forget that the filename is still attacker-controlled input that can escape that folder entirely.

5. Race Condition During Upload Validation

What it is: The server follows a flawed sequence: save the file first → validate it afterward → delete it if it's bad. This creates a brief window where a malicious file exists and is technically accessible before it gets removed.

How it works:

  1. Attacker uploads the malicious file once.
  2. Immediately, they fire many rapid requests trying to access/execute that file (often automated with a tool like Burp's Turbo Intruder).
  3. If even one request lands before the validation/deletion step completes, the file executes.
  4. On that single successful execution, the attacker often has the shell copy itself to a different, permanent location — so even after the original is deleted, they retain access.

Why it happens: This is a timing/logic flaw, not a filtering flaw — the validation is technically correct, but it runs after the file is already reachable instead of before.
