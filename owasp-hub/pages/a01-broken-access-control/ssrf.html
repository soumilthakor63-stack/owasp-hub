Concept & Theory: SSRF

What it is:

SSRF is a vulnerability where an attacker manipulates a server into sending HTTP requests to a destination the attacker chooses, instead of the destination the application intended. The attacker never sends the request themselves — they trick the server into sending it on their behalf.

How it works, at a high level:

Many applications have features where the server fetches a URL based on user input — checking stock from a partner API, generating a link preview, importing a file from a URL, etc. If the app doesn't restrict where that URL can point, an attacker can substitute it with an internal or restricted address.

Since the request comes from the server itself — which usually sits inside a trusted network and is allowed to reach internal systems — it can access things the attacker could never reach directly. The server acts as an unwitting proxy for the attack.

Why it's dangerous:

It can expose internal admin panels, cloud credentials, internal APIs, and databases, and in some cases lead to remote code execution — all without the attacker ever having direct network access to those systems.

Sub-Vulnerabilities

1. Basic SSRF (Against Back-End Systems)

The most direct form. The app takes a URL from user input (e.g. stockApi=http://partner-api.com/check) and fetches it server-side. An attacker replaces it with an internal target — either the server's own loopback (localhost/127.0.0.1) or another internal machine on the private network (192.168.x.x, 10.x.x.x).

These internal endpoints are often unauthenticated because they were never expected to be reachable from outside — the SSRF breaks that assumption and lets the attacker read internal admin panels or trigger internal actions directly.

2. SSRF With Blacklist-Based Filter Bypass

Some apps defend by blocking known-bad strings like localhost or 127.0.0.1. This is weak because there are many equivalent ways to express the same address that the blacklist doesn't recognize — alternate IP notations (127.1, decimal, octal forms), a domain the attacker registers to resolve to 127.0.0.1, case variation, or URL-encoding.

The filter checks the text of the input, but the server acts on how that text actually resolves — and that gap is what gets exploited.

3. SSRF With Whitelist-Based Filter Bypass

Whitelists only allow a specific trusted domain, which sounds much safer — but naive implementations that use simple string checks (instead of a proper URL parser) can be fooled by URL-parsing quirks:

  • Embedding fake credentials before an @ symbol so the "real" host comes after it.
  • Using a # fragment to make a blocked host appear in the string without it ever being sent to the server.
  • Using the trusted domain as a subdomain of an attacker-owned domain.

The filter sees the trusted name; the actual connection goes somewhere else entirely.

4. Blind SSRF

Here, the server does make the malicious request — but the response is never shown back to the attacker. This lowers the immediate impact (no direct data leak), but it's still valuable:

The attacker can confirm the vulnerability exists using out-of-band detection (making the server call a domain the attacker monitors, like a Burp Collaborator URL), then use that same blind channel to scan internal infrastructure or trigger known actions (like a delete/reset endpoint) even without reading any response.

5. SSRF via Chained Vulnerabilities

Sometimes SSRF can't be triggered directly because of strict filtering, so it's combined with another bug to route around the restriction:

  • Via Open Redirect: If the app only allows URLs on its own trusted domain, an attacker can submit a trusted URL that itself redirects (via an unrelated open-redirect feature) to the real internal target. The filter validates the first, legitimate hop; the server then follows the redirect straight into the internal system.
  • Via XXE: If an app parses XML input and resolves external entity references, an attacker can embed a URL inside the XML body itself. The XML parser fetches it server-side — achieving SSRF without ever touching a URL parameter, hidden entirely inside the data format.
