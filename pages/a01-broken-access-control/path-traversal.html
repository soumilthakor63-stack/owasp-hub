Concept & Theory: Path Traversal

Description

Path Traversal (also called Directory Traversal) is a web application vulnerability that lets an attacker access files outside the folder the application intended to expose — by manipulating a file path parameter the app didn't properly validate.

Why it happens

Many apps load files like this: full_path = base_folder + user_input

The app assumes user_input will always be a harmless filename (like logo.png). But if the app doesn't check what's actually inside user_input, an attacker can insert special path characters to redirect that path somewhere else entirely — like a config file, credentials file, or system file (/etc/passwd, win.ini, etc.), reading data that was never meant to be public.

The core mechanic

The ../ sequence means "go up one folder level" — completely normal in any filesystem. Path Traversal weaponizes this by injecting ../ (or equivalent tricks) into user input so the app's file-read function walks backward out of its intended folder, then forward into a sensitive one.

Impact: Exposure of application source code, credentials, sensitive OS files — and in some cases, if the app also lets you write files, full server compromise.

The 3 Variants

1. Basic Traversal (../)

What it is: No defenses at all. The app blindly appends user input to a base path.

How it works: filename=../../../etc/passwd

This directly climbs up folder levels to the root, then descends into etc/passwd. Purely mechanical — no tricks needed, since nothing checks the input.

When you'll find this: Legacy apps, poorly-reviewed code, quick internal tools — anywhere file-serving logic was written without security review.

2. Traversal with Filter Bypass (encoding, null bytes)

What it is: Here, the app does try to defend itself — usually by searching for and stripping the literal text ../ from input. But detection ≠ prevention. Attackers disguise the traversal so the filter doesn't recognize it, while the underlying system still interprets it correctly later.

Common disguises:

  • Nested sequences: ....// — if the filter removes ../ only once, the leftover reassembles into ../
  • URL encoding: %2e%2e%2f (or double-encoded %252e%252e%252f) — filter checks raw text, but something downstream decodes it back into ../
  • Null bytes: ../../../etc/passwd%00.png — historically, filesystem APIs stop reading at %00, silently ignoring anything after it (like a required extension check)

The pattern: The filter looks for one exact "bad string," but doesn't account for equivalent representations of that same string.

3. Traversal with Validation of Start/End of Path Bypass

What it is: Here the app validates the shape of the input rather than its raw content — checking that it starts with an expected base folder, or ends with an expected file extension. This feels stronger, but only checks the edges of the string, not what happens once the path fully resolves.

Start-of-path bypass: App requires input to begin with /var/www/images — attacker just includes that prefix, then adds traversal after it:
filename=/var/www/images/../../../etc/passwd
Passes the "starts with" check, but still resolves outside the folder.

End-of-path bypass: App requires input to end in .png — attacker uses the null byte trick above so the real file read stops before the fake extension is ever reached.

The pattern: Validating only the beginning or end of a string says nothing about where the path actually ends up once every ../ and encoded character is resolved.
