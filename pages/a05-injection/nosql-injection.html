Concept & Theory: NoSQL Injection

What is NoSQL Injection?

NoSQL injection is a web application vulnerability that occurs when user-supplied input is inserted into a database query without being properly validated or sanitized. This allows an attacker to alter the logic of the query itself — instead of just supplying data, the attacker supplies instructions.

This is the exact same root cause as classic SQL injection, but it targets NoSQL databases (like MongoDB, Redis, Cassandra, CouchDB) instead of traditional SQL databases.

Why NoSQL databases are different

Unlike SQL databases, which all speak one common language (SQL), NoSQL databases don't share a single query language — each one has its own syntax and operators. This guide focuses on MongoDB, the most widely used NoSQL database.

MongoDB stores data as flexible, JSON-like documents rather than rigid rows/tables, and in some contexts (like the $where operator) it allows raw JavaScript expressions to be used as part of a query. This flexibility is powerful for developers — but dangerous when user input is not properly controlled.

The Three Main Variants

1. Basic NoSQL Injection — Auth Bypass via Operator Injection

What it is: MongoDB supports special query operators (starting with $) that can be substituted in place of a plain value. Common operators include $ne (not equal to), $gt (greater than), $regex (matches a pattern).

How the attack works: A typical login request sends plain JSON: {"username":"wiener","password":"peter"}. If the backend doesn't strictly enforce that password must be a plain string, an attacker can submit an object instead: {"username":"administrator","password":{"$ne":"invalid"}}.

This tells MongoDB: "find a user named administrator whose password is not equal to the literal string 'invalid.'" Since real passwords are never literally "invalid," this condition is always true — logging the attacker in without knowing any valid password.

2. Extracting Data via NoSQL Operators (Blind Boolean-Based)

What it is: Once operator injection or syntax injection is confirmed, an attacker can ask the database a series of true/false questions about data they can't otherwise see — and reconstruct that data one character at a time by observing how the response changes.

How the attack works: Using syntax injection (breaking out of a quoted string) or the $regex operator, an attacker submits queries like: administrator' && this.password.match(/^a.*$/) && '1'=='1

This asks: "does the administrator's password start with the letter 'a'?"

  • If the response looks like a successful/normal response → the guess is correct
  • If the response looks like a failure/error response → the guess is wrong

By repeating this test for every letter, an attacker can reconstruct an entire secret value without ever seeing it directly. When there's no visible difference, attackers fall back to time-based blind injection — injecting a deliberate delay (e.g. sleep(5000)) that only triggers if the condition is true.

3. NoSQL Injection via JavaScript Injection ($where)

What it is: Certain MongoDB query contexts — most notably the $where operator — allow raw JavaScript expressions to be evaluated as part of the query, server-side. If user input reaches this context without sanitization, an attacker can inject arbitrary JavaScript logic.

How the attack works: Since NoSQL databases have no fixed schema, an attacker often doesn't know what fields exist. JavaScript's Object.keys(this) function can be injected via $where to enumerate field names directly:

"$where":"Object.keys(this)[1].match('^.{0}a.*')"

This asks: "does the second field name in this document start with the letter 'a'?" Repeating this allows an attacker to discover hidden or undocumented fields (e.g., pwResetTkn), which can then be extracted using the character-by-character technique.

Root Cause & Prevention

Key Concepts

  • Syntax injection: breaking out of a quoted string (using ') to inject your own query logic — the NoSQL equivalent of classic SQL injection's ' OR '1'='1.
  • Operator injection: submitting a JSON object (e.g., {"$ne": "..."}) in place of an expected plain value, hijacking the query's logic entirely.
  • Blind injection: extracting data indirectly through true/false signals (response content or timing) rather than seeing it directly in the response.
  • JavaScript injection ($where): the most powerful variant, allowing arbitrary server-side JavaScript execution within the query context.

Prevention

All three variants share the same underlying flaw: untrusted input is trusted as part of query logic. Developers can prevent this by:

  1. Allowlisting input — accept only expected characters/formats, rather than trying to block "bad" ones.
  2. Enforcing strict data types — reject a password field if it arrives as a JSON object instead of a plain string.
  3. Using parameterized queries — ensuring user input is always treated as pure data, never as executable query logic.
  4. Disabling or restricting $where and similar JavaScript-evaluating operators wherever possible, since they carry the highest risk of arbitrary code execution.
