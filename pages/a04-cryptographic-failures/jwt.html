Concept & Theory: JWT Vulnerabilities

What is JWT?

JWT (JSON Web Token) is a compact, self-contained way to represent information as a signed piece of text, so it can be safely passed between a client (browser/app) and a server, or between two servers.

It looks like this: header.payload.signature

Three parts, separated by dots, all just Base64-encoded JSON (except the signature, which is a cryptographic hash).

Why do we need it?

The old way (session-based auth):

  • You log in with username/password
  • Server creates a "session" and stores it in its own memory/database
  • Server gives your browser a session ID (cookie)
  • Every request you make, server looks up that ID in its storage to check "who is this, are they logged in?"

Problem: the server has to store and look up data for every single request, for every user. This gets heavy when:

  • You have millions of users
  • You have multiple servers (e.g., load-balanced) — they'd all need to share that same session storage
  • You have separate systems (mobile app, website, third-party APIs) that all need to verify who the user is

The JWT Way (Stateless Auth)

Instead of the server storing your session, it gives you a signed token that contains your identity info directly inside it. On future requests, the server doesn't need to look anything up — it just re-checks the signature to confirm the token is genuine and unmodified, and reads your identity straight from the token itself.

This is called stateless authentication — the server doesn't need to "remember" you; the token proves it on its own.

Why this matters for security

Since the payload's data is just plain readable JSON (not encrypted, just encoded), and the signature is the only thing protecting it from being tampered with — the entire security of a JWT system rests on that signature being generated and verified correctly. That's exactly why all 7 attack variants below exist: they're all different ways of breaking, bypassing, or exploiting weaknesses in that one signature check.

The 7 Attack Variants

1. Accepting arbitrary signing algorithm (alg: none)

What it is: The JWT header itself tells the server which algorithm to use to verify the signature. JWT supports a special value, alg: none, meaning "this token is intentionally unsigned."

How it works: Attacker changes the header's alg to none, removes the signature (keeping the trailing dot), and edits the payload freely (e.g., role: admin). If the server doesn't explicitly block unsigned tokens, it accepts the forged token with zero verification.

2. Weak signing secret (brute-forceable)

What it is: HS256 tokens are signed using a single secret string, similar to a password. If that secret is weak/common, it can be guessed.

How it works: Attacker takes their own valid signed token and tries thousands of common secrets offline (using a tool like hashcat), recomputing the signature each time until one matches. Once found, they can sign any forged token themselves, with full validity.

3. JWT header parameter injection (jwk)

What it is: The jwk header field lets a token embed its own public key directly, so the server can use that key to verify the signature.

How it works: Attacker generates their own key pair, signs a forged token with their own private key, then embeds their matching public key in the jwk header. A careless server checks the signature against the embedded key instead of its own trusted key — so it "verifies" successfully, even though it was self-signed by the attacker.

4. JWT header injection (jku)

What it is: Same idea as jwk, but instead of embedding the key directly, the header supplies a URL the server should fetch the key from.

How it works: Attacker hosts a JWK Set (their own public key) on a server they control, forges a token pointing jku to that URL, and signs it with their private key. If the server doesn't restrict which domains it trusts for jku, it fetches the attacker's key and validates the forged signature successfully.

5. JWT header injection (kid path traversal / SQLi)

What it is: The kid (Key ID) header tells the server which stored key to use for verification — often by looking up a file path or database row.

How it works: If kid isn't sanitized, an attacker can manipulate it to point elsewhere:

  • Path traversal: point kid to a predictable file the server can read (e.g., /dev/null, which is empty) — then sign the token using an empty string as the secret, since that's what the "key" resolves to.
  • SQL injection: if kid is used in a database lookup query, inject SQL to manipulate which key gets returned, or extract data.

6. Algorithm confusion (RS256 → HS256)

What it is: Some systems support both symmetric (HS256, one shared secret) and asymmetric (RS256, public/private key pair) signing, verified through one generic function.

How it works: The server's public key (meant only for verifying RS256 signatures) is sometimes publicly available. If the verification code doesn't strictly enforce which algorithm should be used, an attacker can sign a forged token using HS256, treating that public key as if it were an HMAC secret. Since the server ends up using that same public key value for verification, the signatures match, even though nothing was actually kept secret.

7. JWT with unverifiable signature (unverified signature bug)

What it is: A pure implementation mistake — the developer uses the library's decode() function (just reads the token) instead of verify() (actually checks the signature).

How it works: Since decode() never validates the signature at all, an attacker can submit a token with any payload and a completely garbage/random signature — the server never even glances at whether it's valid, and just trusts whatever data is in the payload.
