Concept & Theory: Authentication Vulns

1. Username Enumeration via Different Responses

What it is: A flaw where the website's login (or registration) page reveals whether a given username exists on the system, even if the attacker doesn't know the password.

How it works: When an attacker submits a login attempt, the server responds differently depending on whether the username is valid:

  • Wrong username → "Invalid username"
  • Correct username, wrong password → "Invalid password"

These two distinct messages let an attacker build a confirmed list of valid usernames before even attempting to guess passwords — turning a huge brute-force problem into a much smaller, targeted one.

2. Username Enumeration via Subtle Response Differences (Timing)

What it is: A stealthier version of #1 — instead of different text, the website takes measurably different time to respond depending on whether the username is valid.

How it works: Many login systems only bother checking the password if the username exists first (e.g., "look up user → if found, hash and compare password"). Hashing/comparing a password takes a small but measurable amount of time. So:

  • Invalid username → server returns almost instantly (no password check performed)
  • Valid username, wrong password → server takes slightly longer (it actually processed the password check)

An attacker automates many requests and measures response times statistically, sometimes exaggerating the delay by submitting an unusually long password to make the processing gap more obvious.

3. Brute-Force Protection Bypass (IP-Based)

What it is: A weakness in defenses that block an attacker's IP address after too many failed login attempts.

How it works: Some implementations reset the failed-attempt counter as soon as any successful login occurs from that IP. An attacker exploits this by weaving their own correct credentials into the attack:

  1. Try several passwords against the target username (approaching the limit)
  2. Log in successfully using the attacker's own valid account (resets counter)
  3. Repeat — the attacker never actually gets blocked

Attackers may also bypass IP-based blocking entirely by rotating IPs, or by spoofing headers like X-Forwarded-For if the server trusts them blindly to determine the "real" client IP.

4. Brute-Force Protection Bypass (Account Lock Bypass)

What it is: A weakness in defenses that lock a specific account after too many failed attempts against it.

How it works: Account locking protects against attacking one target hard, but not against a broader strategy. The attacker instead:

  1. Builds a list of many candidate usernames
  2. Picks a very small number of common passwords (fewer than the lockout threshold, e.g., 3 guesses if the limit is 3)
  3. Tries each password against every username, spreading attempts thin ("password spraying") — no single account ever hits the lockout threshold, but across hundreds of accounts, some will match

This also fails to stop credential stuffing — using real breached username:password pairs — because each account is only tried once, never reaching the failed-attempt threshold.

5. Flawed 2FA Logic

What it is: A logic flaw where the second authentication step (verification code) doesn't properly confirm that the same user who completed step 1 is the one completing step 2.

How it works (two common patterns):

a) Simple bypass: After step 1 (password), the server marks the session as effectively "logged in" before the 2FA code is verified. An attacker just navigates directly to logged-in-only pages, skipping the 2FA form entirely.

b) Cookie-swap flaw: The server tracks which account is being verified using a cookie the client can edit, e.g., Cookie: verify=wiener. Sequence:

  1. Attacker logs in with their own valid credentials → gets verify=attacker cookie
  2. Attacker edits this cookie to verify=victim
  3. Attacker submits their own valid 2FA code (received via their own email/device)
  4. Because the server only checks "does this code match what's expected for the account named in the cookie" — and doesn't verify the code actually belongs to that session/account properly — the attacker gets logged into the victim's account without ever knowing their password.

Why it happens: The identity being verified in step 2 is controlled by something the client can edit (a cookie/parameter) instead of being tied to a secure, server-side session established during step 1.

Signal to look for: After step 1, inspect cookies/hidden fields for anything identifying "whose 2FA is being checked" — then try modifying it before submitting step 2.

6. 2FA Brute-Force

What it is: Directly guessing the verification code itself, since it's often just a short numeric code (commonly 4–6 digits).

How it works: A 4-digit code has only 10,000 possible values. If the server doesn't rate-limit or lock out repeated wrong code attempts (or if a "logout after N failures" defense can be automated around), an attacker can simply try every possible code — either directly, or combined with the cookie-swap flaw above (guessing the code while the verify cookie points at the victim's account).

Why it happens: Numeric codes have a small search space by design (easy for humans to type), so without strict rate-limiting, they don't offer real protection against automated guessing.

Signal to look for: Test whether repeated wrong-code submissions are throttled, locked out, or CAPTCHA-gated. If not, the code space is small enough to brute-force with tools like Burp Intruder.

7. Password Reset Broken Logic (Token Leakage / Poisoning)

What it is: Flaws in the "forgot password" flow that let an attacker reset another user's password, either by breaking the token validation logic or by stealing/redirecting the reset token itself.

How it works (two patterns):

a) Broken re-validation: A secure-looking system generates a random, single-use token for password resets (?token=abc123...). However, if the server only checks the token's validity when the link is first clicked, but not again when the new password is actually submitted, an attacker can:

  1. Request a password reset for their own account (gets a valid token)
  2. Visit the reset form using their own token
  3. Remove/ignore the token from the final submission, but change the username field to the victim's
  4. Since the final step never re-checks the token, the server resets the victim's password anyway

b) Password reset poisoning: If the reset link's domain is generated dynamically (e.g., based on the Host header of the request), an attacker can manipulate that header when triggering a password reset request for the victim's email. This causes the system to generate and send a reset link pointing to an attacker-controlled domain. When the victim clicks the legitimate-looking email link, their token is sent straight to the attacker's server.

Why it happens: (a) happens because developers assume the token check at link-click time is "good enough" and forget to re-verify at submission time. (b) happens because the server trusts client-supplied data (like the Host header) to build sensitive URLs, without validating it against a known-safe domain list.

Signal to look for: For (a): try submitting the reset form with a different username than the one your token belongs to. For (b): try manipulating the Host header (or X-Forwarded-Host) on the "request reset" call and see if it changes the domain used in the emailed link.

8. "Keep Me Logged In" / Remember-Me Token Flaws

What it is: Weaknesses in the persistent login cookie that lets users stay logged in across browser sessions without re-entering credentials.

How it works: This cookie is effectively a long-lived master key — if forged or stolen, it grants full account access, bypassing login entirely. Common implementation flaws:

  • Predictable structure: Cookie built from static/guessable values, e.g., Base64(username:timestamp) or even Base64(username:password). If an attacker can create their own account, they can study their own cookie, work out the formula, and forge cookies for other usernames.
  • Fake encryption: Some sites "encode" the cookie with Base64 and assume it's secure — but Base64 is trivially reversible, offering zero real protection.
  • Weak/unsalted hashing: Even with real hashing (e.g., Base64(username:MD5(password))), if there's no salt and the algorithm is identifiable, an attacker can brute-force the password offline — hashing candidate passwords themselves and comparing to the stolen/target cookie, with no server-side rate limit to stop them (since it all happens on the attacker's own machine).

Why it happens: Developers treat the "remember me" feature as a convenience add-on rather than applying the same security rigor as the main login system — even though possessing this cookie is functionally equivalent to knowing the password.

Signal to look for: Decode your own remember-me cookie (try Base64 first). If you see a recognizable pattern (username + hash), test whether that hash matches a known algorithm (MD5, SHA1) applied to a common password — if so, the whole scheme can be brute-forced offline using a candidate password list.
