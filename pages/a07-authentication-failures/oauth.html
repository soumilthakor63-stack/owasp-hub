Concept & Theory: OAuth 2.0

What is OAuth? (with example)

OAuth (Open Authorization) is a way for you to let one app access a specific piece of your data on another app — without giving that app your password.

Simple real-life example: Imagine a photo-printing website called PrintMyPhoto. It wants to print photos from your Google Photos account. Instead of asking you to type your Google password into PrintMyPhoto, OAuth lets this happen instead:

  1. You click "Connect Google Photos" on PrintMyPhoto.
  2. You're sent to Google's own real login page (not PrintMyPhoto's).
  3. You log into Google normally, and Google asks: "PrintMyPhoto wants to view your photos. Allow?"
  4. You click Allow.
  5. Google gives PrintMyPhoto a special, limited access token — a temporary guest pass that only unlocks your photos, nothing else.
  6. PrintMyPhoto uses this guest pass to fetch your photos and print them.

Why this matters: PrintMyPhoto never sees your Google password. The guest pass (token) only allows one specific, limited action. You can revoke this pass anytime, without changing your password. The pass usually expires after some time.

In one line: OAuth lets you safely say "yes, this app can do this one specific thing with my account," without ever handing over the keys to your whole account.

The four roles involved:

  • Resource Owner — you, the user
  • Client — the app requesting access (e.g. PrintMyPhoto)
  • Authorization Server — issues tokens after you approve (e.g. Google's login system)
  • Resource Server — holds your actual data, checks the token (e.g. Google Photos storage)

OAuth 2.0 Authorization Code Flow

This is the standard, most secure OAuth flow.

Resource Owner          Client App              Auth Server
      |                     |                        |
      |--1. Clicks--------->|                        |
      |   "Login with X"    |                        |
      |                     |--2. Redirect: client_id, redirect_uri,
      |                     |     state, scope------->|
      |                     |                        |
      |<--3. Login + consent screen------------------|
      |                     |                        |
      |--4. User approves------------------------->  |
      |                     |                        |
      |                     |<--5. Redirect back with code + state--|
      |                     |                        |
      |                     |--6. Exchange code for token
      |                     |     (server-to-server)------>|
      |                     |                        |
      |                     |<--7. Access token------------|
      |                     |                        |
      |<--8. Logged in------|                        |

Step-by-step explanation:

  1. Clicks "Login with X" — the user clicks a login/connect button on the client app.
  2. Redirect: client_id, redirect_uri, state, scope — the client app sends the user's browser to the authorization server, attaching its identity, the return address, a CSRF-protection value, and what access it wants.
  3. Login + consent screen — the auth server shows the user a login page, then a consent screen.
  4. User approves — the user logs in (if needed) and clicks Allow.
  5. Redirect back with code + state — the auth server sends the browser back to the client app's redirect_uri, attaching a one-time secret code and the original state value.
  6. Exchange code for token (server-to-server) — the client app's own backend server privately sends this code, along with its client_secret, to the auth server — this step never touches the user's browser.
  7. Access token — the auth server verifies everything and returns a real access token to the client app's backend.
  8. Logged in — the client app now considers the user logged in / has access to their data.

Key point: steps 1–5 happen through the browser (visible, attackable). Steps 6–7 happen privately, server-to-server (hidden, safer). Most OAuth vulnerabilities target the visible, browser-facing part of this flow.

OAuth Authentication Vulnerabilities (5 types)

1. Authentication bypass via OAuth implicit flow

In the Implicit flow, the access token is delivered directly through the browser instead of a private code-exchange step. If the app's server blindly trusts a username sent alongside the token — without verifying the token actually belongs to that username — an attacker can submit their own valid token paired with someone else's username, and get logged in as that person.

2. Forced OAuth profile linking (CSRF in the OAuth flow)

If the app doesn't check the state parameter, an attacker can start their own OAuth login, grab the resulting callback link (before using it themselves), and trick a logged-in victim into clicking it. This links the attacker's third-party account to the victim's app account, letting the attacker log in as the victim afterward.

3. OAuth account hijacking via redirect_uri

If the app doesn't strictly validate that redirect_uri exactly matches its real, registered address, an attacker can use a lookalike domain (e.g. real-app.com.evil.com) as the redirect_uri. The victim logs in normally, but their secret authorization code gets sent to the attacker instead of the real app — allowing full account takeover.

4. Stealing OAuth tokens via open redirect

This combines a token exposed through the browser (Implicit flow) with an unrelated "open redirect" bug (a page that blindly forwards visitors to any URL given in a parameter). An attacker sets redirect_uri to point to the app's own vulnerable redirect page, which the auth server trusts (same domain) — but that page then bounces the token further out to the attacker's external server.

5. Flawed scope validation

A token issued for a small, limited purpose (like "read basic profile") gets wrongly accepted by a more sensitive part of the system that doesn't check what the token was actually meant for. This includes scope upgrade — where an attacker's app requests a small scope, but manipulates the process to end up with more access than the user approved.

Hardcoded Client Secret Exposure

Hardcoded Client Secret Exposure

What it is: A website's developer accidentally places a secret — meant to stay private on the server — inside a file sent to every visitor's browser (like a public JavaScript file). Since browser files are downloadable by anyone visiting the site, this "secret" is no longer secret.

How it works:

  1. A developer registers their app with an OAuth provider and receives a client_id (public, safe to expose) and a client_secret (private, must stay hidden).
  2. By mistake, the client_secret gets written directly into frontend JavaScript code instead of staying on the backend server.
  3. Anyone can view the site's source code or download the JS file — no login required — and read the secret in plain text.
  4. With this secret, an attacker can impersonate the real application — for example, exchanging stolen data for valid access tokens.

In one line: A password meant to stay locked away on a private server was accidentally shipped to the public part of the website, where anyone can just read it.
