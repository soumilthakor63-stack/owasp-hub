Concept & Theory: Business Logic Vulns

The Core Idea

A business logic vulnerability isn't a "coding bug" — the code works exactly as written. The problem is that the logic itself (the rules the developers designed) has a flaw that lets someone abuse the intended process.

This is different from something like SQL injection or JWT attacks, where there's a technical flaw. Here, everything technically "works" — there's no error, no crash — but the workflow or business rule can be twisted to do something the designers never intended.

Simple analogy: Imagine a store has a rule "customers can return items within 30 days for a refund." Nothing technically stops someone from buying an item, using it heavily, and returning it right before day 30 for a full refund — that's not a "hack," it's abusing a legitimate process. Business logic vulnerabilities are the software equivalent of that.

The 11 Variants

1. Excessive trust in client-side controls

Server blindly trusts data sent from the browser/app instead of re-checking it itself.

Example: A shopping site calculates the price of an item using JavaScript in your browser, then sends that final price to the server. Attacker just edits the price value in their browser before submitting → pays $1 for a $500 item.

2. High-level logic vulnerability

A flaw in the overall intended process/workflow of the feature itself, at a broad conceptual level (not one specific step).

Example: A password reset flow that emails a reset link to whatever email address is provided in the request — instead of the account's actual registered email — letting an attacker reset someone else's password.

3. Insufficient workflow validation

The application doesn't check whether steps in a multi-step process are completed in the correct order.

Example: An online purchase flow: Cart → Payment → Confirmation. If a user can jump directly to the "Confirmation" step URL without ever completing "Payment," they get the item for free.

4. Flawed enforcement of business rules

A specific business rule exists, but it's enforced incorrectly or incompletely somewhere in the system.

Example: A coupon is supposed to be "one use per customer," but the check is only done against a session, not the account — so logging out and back in lets you reuse it.

5. Low-level logic flaw (rounding errors)

Tiny math/precision mistakes in calculations (especially money) that can be exploited repeatedly for gain.

Example: A currency converter rounds down fractions of a cent. If you can trigger thousands of tiny transactions, those "lost" fractions might be redirected/exploited to slowly accumulate real value (classic "salami slicing" attack).

6. Inconsistent security controls across channels

The same action can be performed through multiple channels (web, mobile app, API), but security checks differ between them.

Example: The website enforces "must verify email before purchase," but the mobile app's API endpoint (doing the same action) forgot to add that same check.

7. Flawed assumption about user behavior

Developers design a flow assuming users will only ever do things "the normal way," not anticipating deliberate misuse.

Example: A hotel booking system assumes people won't cancel and rebook repeatedly, so it doesn't limit that — attacker cancels/rebooks in a loop to exploit a "first-time booking discount" every time.

8. Domain/input validation logic flaws

Input is technically valid (right format, right data type) but logically nonsensical or exploitable, and the app doesn't catch that.

Example: A quantity field accepts negative numbers technically (it's still an integer), so entering "-5" items at checkout might make the total price negative, potentially crediting the attacker's account.

9. Insufficient anti-automation

No protection against a real user's actions being repeated thousands of times automatically (bots/scripts).

Example: No CAPTCHA or rate limit on a "redeem gift card code" endpoint → attacker scripts thousands of guesses per second to brute-force valid codes.

10. Weak isolation on dual-use endpoints

The same API endpoint/functionality is used for two different purposes (e.g., admin and regular users), but doesn't properly separate what each type of user can do with it.

Example: A single /updateProfile endpoint is used both for regular users editing their name, and internally for admins editing user roles — if a regular user can just add a role field to their own request, they escalate themselves to admin.

11. Rating/review/coupon abuse logic flaws

Features meant for genuine feedback or promotions can be repeated or faked because there's no real check on legitimacy.

Example: A "leave a review to get 10% off" promo doesn't check if you actually purchased the product, or doesn't limit reviews per account — attacker spams fake 5-star reviews on their own product from multiple accounts, farming discount codes each time.
