Concept & Theory: HTTP Host Header Attacks

What it is:

The Host header in an HTTP request tells the server which website the client wants to reach. This exists because many websites often live on the same physical server/IP (virtual hosting), so the server needs a way to know "route this request to Site A, not Site B."

Why it's a vulnerability:

The Host header is just a plain text value sent by the client — meaning an attacker can set it to anything. The vulnerability isn't the header itself, it's that many applications trust this value blindly and use it for things beyond simple routing: generating links, making trust decisions, building queries, or deciding where to forward a request internally. Whenever attacker-controlled input gets used as if it were trusted, sensitive logic, that's where exploitation begins.

The 5 Variants

1. Basic Password Reset Poisoning

How it works: Some apps build the password reset link dynamically using the Host header, like: https://[HOST]/reset-password?token=abc123

An attacker requests a password reset for a victim's email, but sends the request with a spoofed Host header pointing to a domain they control. The app generates the reset email using that spoofed host, so the victim receives a link like https://attacker.com/reset-password?token=abc123. If the victim clicks it (or the token gets logged/leaked via the attacker's server), the attacker captures the token and resets the victim's password — full account takeover.

POST /forgot-password HTTP/1.1
Host: attacker-controlled.com

email=victim@target.com

2. Web Cache Poisoning via Host Header

How it works: If the Host header value is reflected somewhere in the page response (e.g., in a canonical link, a script src, or a redirect URL) and that response gets cached by a CDN or reverse proxy, an attacker can poison the cached copy. They send one request with a malicious Host value; the poisoned response gets stored under a cache key that doesn't account for the Host difference. Every subsequent visitor requesting that same cached page then receives the attacker's injected content — turning a single request into a persistent, mass-impact attack.

GET / HTTP/1.1
Host: attacker.com

(If the response reflects this Host anywhere and gets cached, all future visitors get the poisoned version.)

3. Routing-Based SSRF via Host Header

How it works: In modern cloud architectures, a front-end load balancer or reverse proxy often reads the Host header to decide which internal backend server to forward the request to. If this routing logic is misconfigured or overly trusting, an attacker can set the Host header to an internal hostname or IP address (e.g., an internal admin panel, a metadata endpoint, or another service on the private network). The proxy then forwards — or "routes" — the attacker's request into the internal network, effectively turning the public-facing server into a pivot point (classic Server-Side Request Forgery).

GET /admin HTTP/1.1
Host: internal-service.local

(Or a Burp Collaborator domain, to confirm the request actually reached out: Host: your-id.oastify.com)

4. Host Header Authentication Bypass

How it works: Some applications implement access control logic like: "if the request's Host is internal.company.com, treat it as an internal/trusted request and skip authentication." This is a flawed assumption, since the attacker fully controls the Host header value from any external location. By simply setting the Host to the expected "internal" value, an attacker can trick the app into granting access to admin panels or restricted functionality without ever needing valid credentials.

GET /admin/dashboard HTTP/1.1
Host: internal.company.com

5. Ambiguous Request Handling (Host Override Headers)

How it works: Even when the real Host header is properly validated, many applications sit behind proxies and also honor secondary headers meant to carry the "original" host through the proxy chain — like X-Forwarded-Host. These override headers are frequently not validated the same way the main Host header is. An attacker sends a valid, whitelisted Host, but adds one of these secondary headers with a malicious value — and if the app's logic (password reset link, cache key, SSRF routing, etc.) reads the override header instead of/alongside the real one, all the attacks above become possible again, bypassing whatever protection was put on the main Host header.

GET /reset-password HTTP/1.1
Host: real-whitelisted-site.com
X-Forwarded-Host: attacker.com

(Other headers that sometimes get trusted the same way: X-Host, X-Forwarded-Server, X-HTTP-Host-Override, Forwarded: host=...)
