Concept & Theory: Info Disclosure

What is Information Disclosure?

Information Disclosure (also called Information Leakage) happens when a website unintentionally reveals sensitive information — to normal users, or to attackers who go looking for it.

It's not about breaking in through force. It's about a website accidentally leaving something exposed that should have stayed hidden — like a shop leaving its storeroom door open, or a stack of internal paperwork sitting on the front counter for anyone to read.

This information could be:

  • Data about other users (usernames, emails, financial info)
  • Sensitive business/commercial data
  • Technical details about the website's infrastructure (software, versions, file paths, database structure)

Even "boring" technical leaks matter, because attackers use them as puzzle pieces — one small leak (like a software version) can lead them straight to a known, public exploit for that exact version.

The 5 Variants

Variant 1: Verbose Error Messages

What it is: A website shows the raw, technical error straight from its code or database instead of a clean, generic message like "Something went wrong."

How it happens: Developers leave debugging/error-detail settings turned on in the live (production) environment, instead of switching to safe, generic error messages before launch.

What it leaks:

  • Database type and version (e.g., MySQL syntax errors)
  • Full internal file paths (e.g., /var/www/html/config/db.php)
  • Table and column names
  • The programming language/framework in use

How testers find it: Feed unexpected input into forms, search boxes, or URL parameters — a single quote ('), broken data types, or oversized numbers often trigger these errors.

Why it matters: It hands the attacker a "map" of the backend, and is frequently the very first sign of a deeper bug like SQL Injection.

Variant 2: Debug Pages/Endpoints Left Exposed

What it is: Developers build special pages or API endpoints purely to help them test and debug the application (e.g., /debug, /test, /phpinfo.php, /actuator, /console, /status). These are meant to be removed or locked down before the site goes live — but sometimes they're forgotten and stay publicly accessible.

What it leaks:

  • Full environment configuration (phpinfo() shows PHP version, server paths, loaded modules, sometimes even environment variables with secrets)
  • Internal application state, logs, or stack traces
  • In some frameworks (like Spring Boot's Actuator), entire internal API maps, live metrics, or even a way to execute commands

How testers find it: Testers try common debug/admin paths directly, and also check tools like Google dorking or web crawlers/spidering to discover forgotten endpoints not linked anywhere on the visible site.

Why it matters: Debug endpoints are often far more powerful than the leak categories above — some don't just disclose info, they can let an attacker directly interact with internal systems.

Variant 3: Source Code Disclosure (Backup Files, Version Control)

What it is: Instead of running server-side code (like PHP) and sending back just the result, the server accidentally serves the raw source code file itself — or an old backup/version-control copy of it is left sitting on the server, fully downloadable.

Common causes:

  • Leftover backup files: login.php.bak, config.old, index.php~
  • Editor temp/swap files: .index.php.swp
  • Exposed version control folders: .git/, .svn/ — an attacker can rebuild the entire commit history and codebase from these

Why it matters: Source code is a goldmine — it can contain hardcoded credentials, API keys, validation logic (so attackers know exactly how to bypass it), and hidden functionality never meant to be public.

Variant 4: Information Disclosure via APIs/Comments

This variant actually covers two related habits, both boiling down to "leftover developer content that shouldn't be public":

A) Comments in HTML/JS source code
Developers leave notes for themselves directly in the page's source code — visible to anyone using "View Page Source" in a browser. Example:

<!-- TODO: remove before launch - admin panel is at /admin_backup_2023 -->

These comments can reveal hidden URLs, old credentials, or internal logic never meant for public eyes.

B) Over-sharing APIs
Modern websites often fetch data from a backend API as JSON, and the frontend only displays certain fields. But the full API response — including fields the frontend hides — is still visible to anyone who inspects the raw network traffic (e.g., via browser DevTools).

Example: a /api/user/123 endpoint might return:

{
  "id": 123,
  "username": "john",
  "email": "john@example.com",
  "password_hash": "5f4dcc3b5aa765d61d8327deb882cf99",
  "is_admin": false
}

The website's UI might only show the username — but the password hash and admin flag are still sitting right there in the response, readable by anyone.

Why it matters: These are extremely common because developers focus on "what the UI shows," and forget that the full underlying response is always visible to a technical user.

Variant 5: Authentication Bypass via Information Disclosure

What it is: This is where Information Disclosure stops being "just informational" and becomes a direct way to break into an account or system. A small leak reveals something that lets an attacker skip or defeat the login/authentication process entirely.

Common patterns:

  • User enumeration → credential attacks: A login or password-reset form responds differently for valid vs. invalid usernames/emails (e.g., "user not found" vs "wrong password"). This lets an attacker build a list of confirmed real accounts, then focus password-guessing efforts only on those.
  • Leaked tokens/session identifiers: Session tokens, password reset tokens, or API keys accidentally exposed in URLs, error messages, JS files, or server responses can be reused directly to hijack a session — no password needed.
  • Leaked source code revealing auth logic: As covered in Variant 3, exposed source code might reveal a hardcoded admin password, a secret backdoor parameter (e.g., ?debug=true&bypass_auth=1), or a flawed authentication check an attacker can exploit directly.
  • Verbose errors revealing valid credentials/structure: Sometimes error messages during login (Variant 1) leak enough detail (e.g., confirming a username exists) to meaningfully weaken the login process.

Why it matters most: This variant shows why testers care about Information Disclosure at all — a "low severity" leak on its own can become the missing piece that lets an attacker walk straight past authentication, turning a minor finding into a critical one.

Key Takeaway

All five variants share the same underlying pattern:

The application shows more than it should — to someone it shouldn't — because of a mistake, not a "hack."

As a tester, your job is twofold:

  1. Find the leak (often just careful looking — error triggering, checking source, trying common paths)
  2. Prove its impact (can it be chained into something bigger — like account takeover, or full system compromise?)

That second step is what turns a simple observation into a real, reportable vulnerability.
