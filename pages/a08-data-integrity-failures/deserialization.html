Concept & Theory: Insecure Deserialization

1. Serialization vs Deserialization (The Base)

  • Serialization = converting an object (living in memory) into a flat, storable/transmittable format (string/bytes). (Robot analogy: you can't mail a toy robot, so you write down instructions on paper to rebuild it. That paper = serialized data.)
  • Deserialization = the reverse — taking that data and rebuilding the actual object in memory.
  • Real-world use: session cookies, shopping cart data, data passed between microservices.
  • Language-specific names: Python → pickling, Ruby → marshalling, Java → native serialization (Serializable interface), PHP → serialize() / unserialize()

2. Why Deserialization Becomes "Insecure"

  • The danger appears when the data being deserialized comes from an untrusted source (user, cookie, API input) instead of the server itself.
  • Serialized data can encode which class to build, not just plain values.
  • Some classes have magic methods that auto-run the moment the object is rebuilt.
  • If attacker controls the data → attacker can control which class gets built → if that class's magic method does something dangerous → attacker achieves impact (privilege escalation, RCE, etc.)
  • Important nuance: The danger can happen during deserialization itself, before the app's own logic even runs — this is why even strongly-typed languages like Java aren't automatically safe.

3. The Real Attack Flow (Web Pentest Mapping)

Normal flow: Server serializes an object (e.g., session: {username, role, isAdmin}) → Sends it to client (cookie / hidden field / API response) → Client sends it back on future requests → Server deserializes it and trusts it.

Attacker's flow: Intercept serialized data (Burp Suite Proxy) → Deserialize locally to understand structure → Modify object (e.g., isAdmin: false → true) or inject a new object entirely → Re-serialize into the exact expected format → Send back to server (Burp repeater/forward) → Server deserializes blindly → attacker gets elevated access or code execution.

4. Magic Methods — The Trigger Mechanism

Magic methods = special methods that run automatically at certain lifecycle moments, without being explicitly called.

  • PHP: __wakeup() (During deserialization), __destruct() (When object is destroyed/script ends)
  • Java: readObject() (During deserialization)
  • Python: __reduce__() (Controls reconstruction behavior)

Gadget chains: Usually one magic method alone isn't powerful enough. Attackers chain multiple classes together — Class A's method calls Class B's, which calls Class C's — until it reaches something powerful like Runtime.exec().

The 6 Variants of Insecure Deserialization

1. Modifying Serialized Objects

The simplest form. The attacker intercepts a legitimate serialized object, edits a field's value directly, and sends the modified version back.

Example: App sends: O:4:"User":2:{s:8:"username";s:5:"guest";s:7:"isAdmin";b:0;}
Attacker changes b:0 (false) to b:1 (true) — turning a regular user into an admin.

2. Arbitrary Object Injection (PHP)

Instead of just editing values inside the expected object, the attacker injects a completely different class into the deserialization process. PHP's unserialize() doesn't care what class it's told to build — it will construct any class available in the app's codebase.

Attacker crafts a payload declaring a different class name (e.g., Logger or FileHandler) with a dangerous magic method. On deserialization, PHP builds THAT class instead, and its magic method fires automatically.

3. Exploiting Known Deserialization Vulnerabilities in Libraries

Instead of finding a gadget chain yourself, you use publicly known, already-discovered vulnerable chains that exist in common third-party libraries (e.g., Apache Commons Collections in Java, Symfony components in PHP).

Tools like ysoserial (Java) and PHPGGC (PHP) come pre-loaded with dozens of these known chains — you just pick the matching library and give it a command to run. This is the fastest real-world path to RCE.

4. Using Application Functionality to Exploit Deserialization

Sometimes you don't need a magic-method-triggered gadget chain at all — you can exploit deserialization through the app's own normal features/functionality.

Example: An app deserializes a user object and later calls $user->getAvatar(). If you inject an object of a different class that happens to have a method with the same name but dangerous behavior, calling that "normal" application code path becomes the trigger.

5. Developing Custom Gadget Chains

When no tool or public exploit exists, you manually build your own gadget chain by reading the source code.

  1. Find a kick-off gadget — a magic method that fires automatically.
  2. Trace forward to find intermediate gadgets — methods passing data along.
  3. Find a sink gadget — a dangerous method at the end (file write, command execution).
  4. Build a serialized payload that walks through this exact path.

6. Deserialization with Encoded/Hybrid Data Formats

Sometimes the serialized data isn't sent in its raw, obvious format — it's wrapped, encoded, or embedded inside another format.

  • Serialized data might be Base64-encoded before being placed in a cookie.
  • It might be embedded inside a JSON or XML wrapper.
  • PHAR deserialization: A .phar archive can be disguised as a .jpg file (a polyglot file). PHP's phar:// stream wrapper causes its serialized metadata to auto-deserialize when touched by filesystem functions like file_exists().
Tools & Prevention

Tools & Blind Detection

ysoserial (Java) and PHPGGC (PHP) generate malicious serialized objects using known chains.

Blind detection: The URLDNS chain triggers a DNS lookup, working on virtually ANY Java app (no specific vulnerable library needed) → confirms deserialization via Burp Collaborator. The JRMPClient chain triggers outbound TCP.

Prevention / Mitigation

  1. Avoid deserializing user input entirely — use safe formats (JSON, XML with schema).
  2. Integrity checks BEFORE deserialization — use digital signature/HMAC to verify data hasn't been tampered with, validated before calling unserialize().
  3. Avoid generic/native deserialization — write class-specific parsing logic.
  4. Don't rely on "removing gadget chains" — the root cause is trusting untrusted data, not the presence of gadgets.
